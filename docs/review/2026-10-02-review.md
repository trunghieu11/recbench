# Review log — 2026-10-02

This page records the first full review of recbench (v0.1, written earlier the same day), what it found,
and what v0.2 changed. It is written as a learning resource: every bug here is a classic mistake in
recommender-system evaluation, and each one now has a test that would catch it again.

!!! info "Short version"
    The architecture of v0.1 was sound (plugin registries, a DuckDB data pipeline, MLflow tracking, smoke and
    full tiers). But its **numbers were not valid**: two models were trained on the very answers they were
    tested on, sequence models read padding instead of the user's history, and a time-zone bug changed the
    train/test cutoff depending on the computer. v0.2 fixes all of this, adds the simple baselines that
    every benchmark needs, and switches to full-catalog evaluation.

## How the review was done

1. Reading every source file and comparing it with the plan agreed on before implementation
   (the 20 decisions in the [roadmap](../results/roadmap.md#decisions-this-project-is-built-on)).
2. Read-only checks on the smoke splits and the installed libraries (for example, how RecBole pads sequences).
3. An independent planning review that re-derived the most important findings and measured costs
   (memory per dataset, run time of the slowest models).

## Critical findings (results were invalid)

### 1. Test-label leakage

**What was wrong.** Two sequence models (HSTU and TIGER) were trained on a file whose "target" column was
*exactly* each user's first test item, the item they were later asked to predict. A third model
(DCN-V2) was trained directly on the evaluation file of "1 positive + 100 negatives".

**Why it matters.** This is like giving students the exam answers to study from. The models looked
brilliant for the wrong reason: after only 200 training steps, on Last.fm, TIGER and HSTU reached
Recall@10 of 0.81 and 0.71 while every other model stayed at 0.34 or below. A real benchmark can never
show a gap like that from so little training. When one method is suspiciously far ahead, check for
leakage first.

**How it was fixed.** Models now receive a [`TrainView`](../codebase/recommender-api.md), an object that can
only read events *before* the test cutoff and has no path to test files. Sequence models learn from
windows cut from that pre-test history (`src/recbench/methods/seq_trainer.py::sequence_windows`); DCN-V2
learns from pre-test interactions plus random negatives.

**Guarded by.** `tests/test_leakage.py` checks that `TrainView` exposes nothing test-related and that every
training target comes from pre-test history.

### 2. Histories read from the wrong end

**What was wrong.** User histories are stored *right-aligned*: the most recent item sits in the last column
and padding (item 0) fills the left. HSTU and TIGER took the hidden state at position "length − 1",
which is correct only for *left*-aligned data. For a user with 3 items in a 20-slot window they read
position 2, which is padding. 84–100% of test users were affected. The RecBole models had the opposite
problem: trained with RecBole's left-aligned layout, but scored with right-aligned sequences.

**Why it matters.** The model's "summary of the user" was computed from padding, so it was nearly the same
for everyone and personalisation silently disappeared. See
[sequential models](../dictionary/concepts/sequential-and-session.md) for the alignment picture.

**How it was fixed.** One convention everywhere: right-aligned histories, user state taken from the *last*
column. The RecBole adapter converts to RecBole's left-aligned layout
(`src/recbench/data.py::HistoryBatch.left_aligned`).

**Guarded by.** The *copy task* in `tests/test_methods.py`: every user walks item i → i+1 → i+2, so a model
that reads the right end of the history predicts the next item almost perfectly, and one that reads
padding cannot. A second test checks that BERT4Rec's input is identical to RecBole's own training rows.

### 3. A time-zone bug in the cutoff

**What was wrong.** The cutoff timestamp was converted with a database function that silently applied the
computer's time zone: +7 hours on the laptop, 0 hours on a cloud machine. Because H&M timestamps are
whole days, the shifted cutoff pushed every test-day purchase into training: the H&M smoke split had
**zero** test users, and the report still said "finished".

**Why it matters.** The same code produced different splits on different machines, so results were not
reproducible. One dataset was silently not evaluated at all.

**How it was fixed.** All cutoff arithmetic uses integer microseconds in UTC
(`src/recbench/pipeline/materialize.py::cutoffs`), cutoffs are computed on the full dataset (so a smoke
split is a true subset of the full split), equal timestamps are ordered by their row in the source file,
and a split with too few evaluation users now fails loudly (`SplitError`).

**Guarded by.** `tests/test_split.py` computes the cutoffs under three time zones and requires identical
results, checks tie order, and checks the "too few users" failure.

### 4. Stale results would have survived the fix

**What was wrong.** The runner skipped a (dataset, method) pair when an earlier run had finished, without
checking the protocol version or the settings. After fixing the bugs above, the old leaky runs would have
been reused as if they were valid.

**How it was fixed.** Runs are identified by a `config_hash` that includes the protocol version, the code
version, the split's own hash, and every setting (`src/recbench/config.py::config_hash`). The old store was
archived as `runs/mlflow_v1_archive`.

**Guarded by.** `tests/test_runner_serving.py` checks that changing any setting forces a new run.

### 5. Serving could not load most models

Of the four models deployed to Cloud Run, three raised an error when loaded. Serving now uses
[bundles](../codebase/serving-and-bundles.md): precomputed top-100 lists written right after
evaluation, which the API reads without any model code (and without PyTorch). A test checks that the API
returns exactly what the evaluator ranked.

### 6. Managed services were stubs

The AWS and Google calls were not authenticated (AWS needs signed requests, Google an OAuth token), and
no managed service was ever scored. Recombee is now benchmarked end to end on the same data as local
models ([how-to](../how-to/run-recombee.md)); AWS Personalize and Google's commerce recommender are
documented in the [dictionary](../dictionary/algorithms/managed-services.md).

## Plan items that were missing in v0.1

| Planned | v0.1 | v0.2 |
|---|---|---|
| A ladder from simple to complex methods | 9 advanced methods only | 17 methods, rungs 0–7, simple baselines ranked |
| Full-catalog ranking | 1 true item vs 100 random items | full ranking primary, sampled kept as a check |
| Warm vs cold users | everyone scored the same way | warm users primary, cold users a separate slice |
| Repeat consumption | ignored (36–62% of Last.fm test items were repeats) | per-dataset repeat policy, Last.fm reported both ways |
| Confidence intervals | none | bootstrap 95% intervals, ties marked |
| Beyond-accuracy metrics on real lists | computed on the 101 sampled items | computed on full-ranking top-10 lists |
| Honest method names | `generative_llm` had no LLM; `tiger` generated nothing | renamed (`text_hash_tower`, `tiger_lite`), fidelity stated on every page |
| Grounded explanations | fixed sentence templates | explanations cite the user's own history items |
| Per-method memory | memory accumulated across methods | one child process per method |
| Open-source hygiene | no git, licence, or tests of the docs | git, MIT licence, docs checked by tests |

## Smaller fixes

- Steam item text came from user *reviews*, which can be written after the cutoff (content leakage).
  It now comes from the games metadata file (title, tags, genres). The Steam reader also no longer stops at
  the first 5 million lines.
- Last.fm dropped artists that have no MusicBrainz id; they are now keyed by name.
- RecBole re-split its training data and threw away each user's most recent 20%; it now trains on all
  pre-test events. S3-Rec is now pre-trained *and* fine-tuned, as in the paper; BERT4Rec uses the stronger
  cross-entropy loss.
- XSimGCL kept its graph on the CPU even on a GPU machine; graph models now follow the chosen device.
- The multimodal model read real JPEG images as all-black pixels and, on the laptop, used generated
  placeholder "images"; it now reads real images with Pillow and refuses to run without them.
- The Docker image no longer installs PyTorch, the port is consistent (8080), and the Cloud Run service is
  private by default.
